# 스마트 탑승 도우미

## 기존 구조 확인과 통합 범위

| 항목 | 확인한 구현 / 재사용 방식 |
| --- | --- |
| 프레임워크·라우팅 | 의존성 없는 JavaScript ES 모듈, `app.js`의 hash 라우팅. `#boarding`만 추가 |
| 홈·내비게이션 | `home.js`의 나의 일정 카드와 기존 5개 메뉴 유지. 가까운 유효 여정의 도우미 진입 버튼 추가, 도우미에서는 승차권 메뉴 활성화 |
| 승차권 카드 | `tickets.js`의 그룹·날짜·상태·등급색 유지. 추가 요청에 따라 펼침 대신 카드 클릭 → 기존 QR 승차권 화면으로 변경 |
| 승차권 상세 | 기존 `showTicketQR`와 `ticketQR` 재사용. 열차명 아래 차내 시설·운행 정보, 오른쪽 승강장/다음 정차역, 도우미 버튼, 환승·왕복 구간 이동 추가 |
| 예약 저장 | 기존 `raillink-bookings` IndexedDB / `state` 저장소의 `raillink.v1`. 발권·환불·좌석 재고·충돌 검사는 변경하지 않음 |
| 예약 모델 | `id`, `key`, `travelDate`, `serviceDate`, ISO `departure/arrival`, `groupId/groupType`, 좌석·등급·인원 사용. 별도 개인정보 수집 없음 |
| 공통 시간표 | 기존 `RailData`, `model.segment/serviceDate/departure`, `railway-time.js` 재사용. 철도 DB를 별도로 복제하지 않음 |
| 운행 처리 | `operations.js`의 `operationSnapshot/operationPosition`으로 정차·통과·대기·서비스 날짜·지연 처리. 전체 시간표·지도는 기존 `openOperation` 연결 |
| 승강장·등급 | canonical `REAL_PLAT`를 읽는 `_realPlatform`, `GRADE_COLORS`, `SEAT_CLASSES` 사용. 없는 승강장은 미정 |
| 좌석 방향 | 기존 `model.seats`의 방향 판정 재사용. 방향·좌석 요약만 캐시하며 재고 상태를 별도 변경하지 않음 |
| UI | 기존 CSS 변수, 선형 SVG 아이콘, dialog, 토스트, QR 문서, 하단 safe-area 사용. 추가 이미지·패키지 없음 |
| PWA·알림 | 기존 서비스 워커/캐시/설치/업데이트 방식 유지. 별도 push 서버는 없음 |
| 검증 | `npm run check`, `npm test`, `npm run build`, Python Playwright/Chromium 검증 도구 |

원래 사양의 펼침 카드 유지보다 후속 요청의 **승차권 직접 열기**를 적용했다. 도우미는 해당 승차권 화면의 버튼으로 진입한다. 기존 환불·변경·삭제는 목록에 남아 있고, 각 구간의 QR·시설·운행 정보는 승차권 화면에서 계속 이용할 수 있다.

## 화면과 상태

- **탑승 전:** 시간표·예약 기준 출발 카운트다운, 운행일·열차·출도착·소요시간, 실제 등록된 승강장, 좌석·방향, 주요 정차역, QR/운행 정보/일정 파일/공유.
- **탑승 중:** 시간표 기준 예상 위치와 정차시간을 고려한 0–100% 진행률, 다음 정차역 도착·출발·정차시간, 도착 30/10/5분 안내, 좌석과 QR.
- **도착 후:** 여행 요약, 이용 내역, 기존 가상 영수증, 같은 구간 다시 예매, 개인정보를 뺀 여정 공유. 실제 도착 확인이 없으면 **도착 예정 시각 경과 · 운행 상태 확인 중** 표시.
- 단계 탭과 구간 선택은 화면 미리보기일 뿐이다. 예약 상태를 쓰거나 승객의 실제 탑승을 확정하지 않는다. `현재 단계로` / `현재 구간`으로 자동 안내에 복귀한다.
- 홈에서 진행 중 여정을 먼저, 이후 출발이 가까운 여정을 선택한다. 환승 그룹은 하나의 여정으로 취급하며 취소된 승차권과 지난 여정은 홈 활성 일정에서 제외한다.
- 시간 계산은 ISO timestamp와 KST 서비스 날짜의 누적 분을 사용한다. 자정, 전날 시발 열차의 다음 날 승차, 다음 날 도착, 지연·환승의 날짜 변경을 지원한다.
- 환승 대기 = 다음 구간 출발 − 앞 구간 도착. 10분 미만 또는 남은 여유 5분 이하는 주의, 음수는 도착이 다음 출발보다 늦다고 안내한다. 역간/승강장 이동 시간이 없으므로 환승 가능 여부를 확정하지 않는다. 환승역 도착 예정 시각부터 다음 구간을 자동 선택한다.

## 데이터 신뢰도와 갱신

현재 배포 소스에는 실제 실시간 위치·검표·도착 확인 API가 없다. **현재 화면은 시간표 기반 예상**이며 기존 지연 엔진의 값은 **모의 운행 지연**으로 표시한다. 원본 엔진이 기기의 현지 시간을 사용하므로, 기존 정책과 동일하게 기기 시간대가 한국인 경우에만 모의 지연을 반영한다. 시간표·카운트다운 자체는 어느 기기 시간대에서도 KST로 처리한다.

`boardingState`에는 향후 검증된 데이터 연결용 입력 계약이 있다. `verified`, 열차 key, serviceDate, 갱신 timestamp가 맞아야 수용한다. 정차역별 absolute 예상 시각·승강장·위치 설명·운휴·해당 하차역 도착 확인을 구분한다. 현재 운영 코드에 이를 제공하는 서버는 연결되어 있지 않다. 5분 이상 지난 확인 데이터와 오프라인 데이터는 갱신 필요로 표시하고, 이미 확인된 도착 사실은 과거 기록으로 유지한다.

새로운 네트워크 폴링을 추가하지 않았다. 기존 분 단위 갱신에서 보이는 도우미만 갱신하고, visibility/pageshow/online/offline 복귀 때 다시 계산한다. 같은 분의 계산은 재사용하며 완료된 구간은 모의 지연 조회를 계속하지 않는다. 갱신 실패는 마지막 시간표와 실패 문구를 표시한다. 오프라인 재접속은 기존 PWA가 캐시한 공통 시간표와 IndexedDB 승차권을 이용한다. 시간표가 없으면 저장된 승차권 시각만 보이고 위치·정차역을 만들지 않는다. 시간표 계산 시각을 실제 데이터의 갱신 시각으로 표현하지 않는다.

## 접근·저장·개인정보

- 경로는 `#boarding`뿐이고 예약번호·QR을 URL에 넣지 않는다. 선택 ID는 localStorage와 sessionStorage에 보관하며, 진입할 때마다 **현재 이 브라우저의 예약 저장소**에서 유효한 ID인지 확인한다.
- 취소·변경·삭제된 ID 또는 다른 저장소의 ID는 차단한다. 이 서비스에는 계정 서버가 없으므로 서버 기반 사용자 인증·소유자 검증을 구현했다고 주장하지 않는다. 같은 브라우저 프로필의 예약을 다른 실제 사용자와 분리하려면 향후 계정 시스템이 필요하다.
- 공유는 열차명·구간·날짜·시각만 포함한다. 예약 ID·좌석·승객 정보·QR은 공유와 일정 파일에서 제외한다. 공유 API가 없으면 클립보드, 둘 다 없으면 비활성화한다.
- 일정은 표준 ICS 다운로드(UTF-8 줄 접기, 임의 UID, UTC absolute 시각). 사용자가 일정 앱에서 추가한다. 캘린더 계정에 자동 등록하지 않는다.
- QR은 기존 발권 함수 그대로 사용한다. 가상 발권이며 실제 철도 검표에 쓸 수 없음을 명시한다.

## 알림

- 앱이 보이는 상태에서 출발 60/30/10분, 도착 30/10/5분 구간, 관찰된 시각·승강장·지연 변경, 환승 여유 부족을 확인한다. 처음 실행할 때 이미 지나간 임계값들을 한꺼번에 발송하지 않는다.
- 기존 앱 안 알림 설정과 명시적인 시스템 알림 권한을 따른다. 거부·미지원 시 기본 기능과 앱 안 안내는 유지한다.
- 예약 ID·이벤트 종류·예정 시각별로 중복을 막는다. 최근 최대 250개 ID만 로컬 저장하며 저장 불가 시 실행 세션 내 중복 방지는 유지한다. 출발·도착 시각 변경 시 새 시각으로 다시 계산한다.
- 홈 알림 버튼에서 해당 승차권 도우미를 열 수 있다. 시스템 알림은 지원 시 service worker `showNotification`, 그 외 지원 브라우저는 `Notification` 사용.
- 알림 클릭은 열려 있는 클라이언트에 메시지를 보내고 현재 저장소에서 ID를 다시 검증한다. 닫힌 뒤 이미 표시된 알림을 클릭하면 기존 IndexedDB의 별도 일회성 키를 통해 해당 여정을 복원한다(5분 유효, 읽고 삭제). URL에는 ID가 없다.
- **앱 종료 상태의 예약 알림 생성·백그라운드 타이머·서버 푸시는 제공하지 않는다.** 실제 승강장 변경·운휴·지연 푸시는 공식 공급 데이터와 푸시 서버가 필요하다.

## 파일 구성

- `js/boarding.js`: 시간·상태·진행률·구간·공통 데이터 어댑터, 좌석 요약, 공유/ICS.
- `js/boarding-view.js`, `css/boarding.css`: 세 단계 반응형 화면.
- `js/boarding-controller.js`: 진입, 예약 검증, 선택/미리보기/복원, 빠른 메뉴, 가시성 갱신.
- `js/boarding-notifications.js`: 이벤트 판정, 중복 방지, 앱 실행 중 알림.
- `js/app.js`, `js/home.js`, `js/tickets.js`, `css/ticketing.css`: 라우트·홈·승차권 통합과 직접 열기.
- `js/styles.js`, `index.html`, `sw.js`: 릴리스별 CSS 로딩과 알림 클릭.
- `tests/boarding.test.mjs`, `tools/verify-boarding.py`: 순수 계산·데이터 경계와 실제 브라우저 통합 테스트.
- 기존 `verify-home/journey/ticketing/storage.py`: 승차권 직접 열기 흐름에 맞춰 테스트 경로 변경, 검증 내용 유지.

## 검증 및 남은 범위

단위 테스트는 출발 2시간/30분/5분, 진행/도착 경계, 정차 중 진행률, 통과역 제외, 확인/추정/누락/오래된 데이터, 취소·다른 ID, 야간·서비스 날짜, 앞/뒤 구간 시각 변경, 부족한 환승 여유, 캐시 실패, 알림 기준, ICS·공유 정보 최소화를 검증한다.

브라우저 검증은 실제 공통 데이터로 예매한 직통·환승 승차권을 사용한다. 홈/승차권 진입, 직접 QR 열기, 미리보기의 예약 불변성, 분 갱신 시 포커스, 새로고침, 취소·없는 ID 차단, 자동 환승 전환, 기존 운행 정보와 영수증, ICS, 오프라인, 320/390/480/768/1280 CSS px, 다크모드를 확인한다. 480×1040은 S24+ 1440×3120의 3배 배율에 해당하는 CSS 기준이다. 물리 기기의 상태바·제조사 브라우저·실제 스크린리더 및 OS 알림 표시는 별도 기기 검증이 필요하다.

역 내부 지도·승강장 이동시간 데이터가 없어서 지도 버튼은 미제공 상태다. 실시간 확인 서버, 승객 탑승 검증, 운휴 피드, 실제 운행 지연 이력, 서버 푸시, 계정 간 동기화는 새로 만들지 않았다. 이들을 연결하려면 공급 데이터·서버 기반이 필요하다. 현재 구현은 제공된 데이터가 보장하는 범위만 안내한다.

검증 실행 결과: `npm run check`(42개 JS 파일 문법 검사), `npm test`(10개 테스트 파일, 48개 선언된 테스트), `npm run build` 통과. `verify-boarding.py`, `verify-home.py`, `verify-journey.py`, `verify-ticketing.py`, `verify-storage.py` 브라우저 검증 통과. 화면 캡처는 로컬 `artifacts/boarding/`에 저장했으며 저장소에는 예약 예시 캡처를 커밋하지 않는다.
